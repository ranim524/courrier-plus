# Physical Delivery

## Purpose
Manage the real physical delivery of a printed letter from Courrier+ to the recipient — the *only*
way a recipient is ever notified, since there is no digital access-link flow anymore (see
[[security]]).

## When to use it
Any time you touch `app/models/delivery.py`, `app/services/delivery_service.py`, `app/services/delivery_state.py`, `app/services/delivery/`, `app/routes/delivery.py`, `app/routes/delivery_confirmation.py`, `app/routes/delivery_webhook.py`, or the delivery-related field on `TrackingRead`.

## Project conventions
- One `DeliveryOrder` per `Letter` (unique FK), auto-created by `delivery_service.create_delivery_order()` right after a letter reaches `SENT` (called from `payment_service.confirm_payment()`). It's immediately advanced to `READY_FOR_DISPATCH` — the prototype has no separate "printed"/"prepared" step to wait on.
- Detailed physical status lives on `DeliveryOrder.status` (`DeliveryStatus`, see `delivery_state.py` for the full transition graph): `... -> OUT_FOR_DELIVERY -> DEPOSITED -> DELIVERED`. `Letter.status` only ever leaves `SENT` via `_finalize_delivery()`, landing on `RECEIVED` (if `acknowledgment_of_receipt` was requested — that `ProofOfDelivery` *is* the accusé de réception) or `DELIVERED` otherwise. See [[database]].
- **Deposit and confirmation are deliberately two separate functions**, not one: `mark_deposited()` (letter physically placed in the mailbox — called by an admin for the manual provider, or `mark_deposited_by_tracking_number()` from the webhook for an external one) only emails the recipient a confirmation request; `confirm_delivery_by_recipient()` (public, token-scoped) and `force_confirm_delivery()` (admin fallback) both funnel into the shared `_finalize_delivery()`, the only place that creates the `ProofOfDelivery` and emails the sender. Never collapse these back into one step — that's exactly the "livreur informe sa plateforme -> plateforme informe la nôtre -> on notifie" flow this was built for.
- The recipient's confirmation token (`DeliveryOrder.confirmation_token_hash`) follows the exact same hash-only-storage, single-use discipline as everything else token-shaped in this project — see [[security]]. Generated by `generate_secure_token()`/`hash_token()` (`app/core/security.py`), the same functions used elsewhere, not a new implementation.
- Provider abstraction mirrors [[payment]]/document-management's storage pattern exactly: `app/services/delivery/base.py` (`BaseDeliveryProvider`), `app/services/delivery/manual_provider.py` (`ManualDeliveryProvider`, phase 1 — no external API, all status changes come from admin actions), `app/services/delivery/__init__.py` (factory keyed by `DeliveryProvider.code`). A real carrier is added later as a new provider class + DB row, reporting deposits through `app/routes/delivery_webhook.py` instead of the admin UI — never by hardcoding a company name into `delivery_service.py` or routes.
- Audit events reuse the existing `letter_events` table/`LetterEventType` enum (`DELIVERY_CREATED`, `DELIVERY_ASSIGNED`, ... `DELIVERY_DEPOSITED`, `DELIVERY_DELIVERED`, ... `DELIVERY_CANCELLED`) — no separate `delivery_events` table, since every delivery event is already scoped to exactly one letter.
- Tracking number format `CP-2026-0001847` (`app/utils/tracking_number.py`), generated the same way as the letter reference (`app/utils/reference.py`): random, unique (DB constraint + retry loop), never the row's UUID. This is what an external carrier's webhook payload identifies a delivery by (`mark_deposited_by_tracking_number`) — it never sees our internal `DeliveryOrder` UUID.

## Important rules
- **Only a confirmed `DELIVERED` means the physical letter reached the recipient AND they said so.** `DEPOSITED` alone (physically placed) is not enough — no status up to and including `DEPOSITED` may trigger the sender's "your letter was delivered" email. `_finalize_delivery()` is the *only* function that sends `DELIVERY_CONFIRMED_SENDER` or creates a `ProofOfDelivery`, reached only via `confirm_delivery_by_recipient()` or `force_confirm_delivery()`.
- `_finalize_delivery()` is idempotent: confirming an already-`DELIVERED` order is a no-op (checked before any state change) — never a second proof, event, or email, regardless of whether the repeat call came from the recipient's token or an admin's force-confirm. See [[testing]]'s critical email test.
- The recipient never gets a second email confirming their own confirmation — only the sender is emailed by `_finalize_delivery()`. If a UI needs to show the recipient something, it's the confirmation page's own success state, not another email.
- `DELIVERED` is terminal — no administrative "undo" transition exists (deliberate, not an oversight). All status changes go through `delivery_state.transition()`, same explicit-allow-list pattern as `letter_state.py`.
- Every admin-mutating delivery endpoint lives under `/api/admin/deliveries/*` (or `/api/admin/delivery-agents/*`), behind `get_current_admin`. The two exceptions are deliberately narrow: `/api/delivery-confirmation/{token}` (recipient, scoped to exactly one delivery by a single-use token, never exposes letter content) and `/api/webhooks/delivery/deposited` (external carrier, scoped by `X-Webhook-Secret`, never an admin JWT).
- No API credentials are ever stored on `DeliveryProvider` rows, even for a future external carrier with `api_enabled=True` — they belong in environment variables, referenced by the provider's `code`. The webhook secret (`DELIVERY_WEBHOOK_SECRET`) follows the same rule and is compared with `hmac.compare_digest`, never `==`. See [[security]].
- The public view (`GET /api/track/{reference}`) exposes a `DeliveryPublicView` derived only from `DeliveryOrder`'s own timestamp columns — never courier name/phone, admin notes, or internal UUIDs. Built by `delivery_service.to_public_view()`. The recipient confirmation view (`DeliveryConfirmationView`) is even narrower on purpose: no letter subject/message/PDF, ever.
- `DeliveryAttempt` rows are created only on failure (`mark_failed`); a successful delivery gets a `ProofOfDelivery`, not an attempt row.

## Workflow to add a new admin action
1. Add the transition to `ALLOWED_TRANSITIONS` in `delivery_state.py` if it's a new edge.
2. Add the function in `delivery_service.py`: call `delivery_state.transition()`, set the relevant timestamp column, record the matching `LetterEventType`, commit.
3. Add the route in `app/routes/delivery.py` (admin-only), calling the service function and returning `delivery_service.to_read()`.
4. Add a test in `tests/test_delivery.py` (service-level) and/or `tests/test_delivery_routes.py` (API-level).

## Testing gotcha
The test DB schema is built via `Base.metadata.create_all()` (see [[testing]]/conftest.py), not by running real Alembic migrations — so seed data a migration inserts (the `courrier_plus_internal` provider row) must also be seeded in `conftest.py`'s `_seed_reference_data()`. Similarly, adding a new Python-side enum member (`LetterEventType`, `EmailType`, `DeliveryStatus`, etc.) does **not** alter the actual Postgres enum type in a real deployment — that needs an explicit `ALTER TYPE ... ADD VALUE` migration (see `43aa24b4be43_add_delivery_event_and_email_enum_values.py`) even though `create_all` masks this gap in tests. This exact gap broke delivery event recording the first time it was tested live — always verify a new enum member against the real dev DB, not just the test suite, before considering it done.
